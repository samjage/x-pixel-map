Q1. PFP driver and modes
- CERTAIN register map (stream1 FUN_0086d3d8/4b0/5a8/664/77c/7fc/8c8/884):
    c000: bits 0-2 = mode (written at start), bit 8 = pixel packing flag (still: (ctx+0x49c & 0x10)==0), bit 16 = on.
    c004 = image address (still: buffer + ctx[0x498]*2). c008 = stride (13 bit).
    c00c = list address (8-aligned, hence the 64-bit A padding). c010 = count (< 0x40000; the driver splits larger lists).
    c014 = value & 0x13ff13ff. It is always 0, from the struct field +0x18 (DAT_0156da50) and in live view.
    c018 = status (read). c01c = IRQ ack (0x1f). c020 = IRQ mask.
    c030..c22c = 128-word weight table from 0x146bcf0.
  Driver chain: FUN_0117a84c -> FUN_010cb46c (copies struct, loads table, list regs, splits >0x3ffe0 records)
  -> FUN_010cb300 (start, mode) -> wait event 0x30.
- CERTAIN who uses which mode:
    Still per-shot setup FUN_0116a1e4: mode 1 = main lists (needs cfg 0xb4 bit 2), mode 3 = sub/AF lists (cfg 0xb4
    bit 3). Either becomes mode 4 if cfg 0xc9 bit 2 / bit 3 is set.
    Second user, live view / movie: FUN_01355ed0 -> FUN_0120f4c8. Always mode 3 (mode 4 if cfg 0xc9 bit 7). Gated by
    cfg 0xb4 bit 7 (0 on this camera, so it is OFF). Lists from table 0x13c55f0 via FUN_010cd16c.
    FUN_0120f4c8 loads the weight table only when mode < 3.
    Mode 2 is never used. Mode 0 is rejected by the driver.
- GUESSED meanings:
    Modes 1 and 2 = weighted replacement using index cls*16 + flag*8 + aux (see trace_pfp).
    Mode 3 = an AF-pixel defect mode that does NOT use the weight table, so cls, aux and flag are probably ignored.
    Mode 4 = a factory debug mode (forced by the 0xc9 debug bits).
- What mode 3 does to image values, and whether mode 1 skips AF positions, is UNRESOLVED. The evidence:
    (a) Factory list1/list3 AF pixels look exactly like unlisted AF pixels in every dark set, whether or not their
        list is active (aflisted.py). They are not dark-current defects. Probably they are bad phase/sensitivity
        pixels, which matter for AF.
    (b) Your list1 entry (mode 3) changed nothing in the RAF.
    (c) Your list2 entry (mode 1, P1 confirmed active: list2-only pixels are clean in the ISO3200 and 1 s sets,
        l2only.py) also left the pixel's raw value untouched, both at ISO3200 1/180 (not saturated) and at 1 s.
        Ordinary list0/list2 pixels are corrected (temporal sd 0.58x random).
  So with these records the PFP did not modify that AF-lattice position.
- Lead (CERTAIN data, GUESSED meaning): the live-view list at cfg 0x5d510 (count u16 at cfg 0x279c = 4; the other
  eight live-view lists are empty) holds 32-bit records (x u16, y u16): (2772,405), (2022,432), (2358,517),
