X-T1 / EXR PROCESSOR II UNBRICK RESEARCH REPORT
================================================
Date of research: 2026-11-04. Web only. No devices touched, nothing downloaded or run.
Target: Fujifilm X-T1 (EXR Processor II, fw 5.52) and same-generation EXR II bodies
(X-E2, X-E2S, X-T10, X100S, X100T, X30, X70, X-A1/A2, X-M1, XQ1/2).

Evidence labels:
  VERIFIED     = someone reports doing it successfully on real hardware
  CLAIMED      = stated by a developer or source, but no hardware report found
  SPECULATIVE  = my inference, or an untested idea

Languages searched: EN, JA, ZH (simplified), RU, DE, FR, IT, KO.
Non-English searches turned up nothing useful. No Japanese, Chinese, Russian, Korean,
German, French or Italian source describes an EXR II unbrick. All the substantive material
is in English, in a few GitHub projects (fffw, fujimod, fujihack) from 2026.
I found no public report of an X-T1 bricked by an *official* firmware update. Fuji's
known X-T1 firmware problems (4.20 AF-C freeze, 5.50 XC15-45 incompatibility) were
functional bugs that later firmware fixed, not bricks.

-------------------------------------------------------------------------------
TOP FINDINGS (ranked by usefulness to a home owner)
-------------------------------------------------------------------------------

1. BOOT-ROM SD-CARD BOOT ("green-LED card" / ffboot.bin + ffsys.bin). This path is independent of NAND.
   What: The EXR-family boot ROM (mask ROM at 0x80000000, 16 KB) can load a stage-0
     loader from a FAT-formatted SD card instead of NAND. You hold a key combination at
     power-on. The card holds:
       ffsys.bin  = hardware configuration data
       ffboot.bin = stage-0 loader
     The loader can be trivial (an LED blink), or it can reprogram NAND, or it can load
     the stock firmware from the card so you can then run the normal on-screen updater.
   Critical detail (fffw wiki): The ROM writes the power-hold register 0xFFF88084 from
     bit 0 of byte 0x10 in ffsys. In the NAND copy of ffsys this bit is CLEAR. That is a
     fail-safe for NAND boot. SD loads are slower, so the camera may power off before a
     loader larger than about one sector finishes loading. The fix is to SET bit 0 of
     ffsys offset 0x10 in the SD image. If you copy ffsys straight from the DAT, the
     camera will look dead even when the ROM did accept the card.
   X-T1 key combo: The fujimod catalog (catalog/bodies/xt1/controls.json, "boot" block)
     gives SD boot = hold AE-L + Fn1. Firmware-update boot = hold DISP/BACK.
     - In the catalog, AE-L is GPIO 0-10 and Fn1 is GPIO 0-11. Fn1 is the FRONT Fn button
       (manual p.39). Fn2 is the top Fn/Wi-Fi button.
     - The same two GPIO lines (0-10, 0-11) are the SD boot combo on other EXR II bodies:
         X-E2: command-dial press + Fn7
         X70:  command-control press + Fn1/movie
       So the X-T1 mapping is consistent. These values are marked "declared catalog
       input", not measured.
     - NOTE: The X-T1 owner in fffw #13 / fujimod #12 tried these combos:
         Movie+FocusAssist, Fn2/WiFi+FocusAssist, FrontFn1+FocusAssist, AE-L+Fn2/WiFi
       They did NOT try AE-L + front Fn1. Their test ffsys.bin was described as
       "provisional", and nothing says they set the power-hold bit.
   Evidence:
     - X70 (EXR II): VERIFIED. fujimod progress shows sd-select "The boot ROM loads a
       green-LED card" = pass, and sd-boot "FujiMod boots from the card" = pass. Several
       X70 owners run FujiMod from SD.
     - X-E2: CLAIMED / partly verified. tiredboffin wrote bare-metal LED code for it
       (fffw/boot/xe2-start.S, xe2-led0-main.c) and says he once reflashed X-E2 NAND
       through his ffre loader.
     - X-T1: CLAIMED only. fujimod progress for xt1/5.52 shows sd-select, sd-boot,
       sd-stock-boot and sd-recovery all "not-run" on hardware. It uses "boot_rom": "X70".
     - "sd-recovery" (a flash-free card that applies an official update) is not-run on
       every EXR II body, so no one has demonstrated the full end-to-end recovery yet.
   Needs: an SD card, a PC, and correct ffsys.bin/ffboot.bin (fujimod.com builds
     "SD boot" / recovery files in the browser from the official FWUP DAT). No soldering.
   Cost: ~free. Risk: low if the loader does not write NAND.
   Sources:
     https://github.com/tiredboffin/fffw/wiki/Note-on-unbricking-EXR-cameras  (EN)
     https://raw.githubusercontent.com/justjake/fujimod/main/catalog/bodies/xt1/controls.json
     https://raw.githubusercontent.com/justjake/fujimod/main/catalog/bodies/xe2/controls.json
     https://raw.githubusercontent.com/justjake/fujimod/main/catalog/bodies/x70/controls.json
     https://raw.githubusercontent.com/justjake/fujimod/main/catalog/progress/xt1/5.52/progress.generated.json
     https://raw.githubusercontent.com/justjake/fujimod/main/catalog/progress/x70/1.10/progress.generated.json
     https://raw.githubusercontent.com/justjake/fujimod/main/catalog/recovery/processors.json
       (exr boot ROM: addr 0x80000000, 16 KB, sha256 7dc7e332...)
     https://github.com/tiredboffin/fffw/tree/main/boot

2. FUJIMOD.COM "RECOVERY" PAGE (official DAT re-flash from an SD-booted stock firmware)
   What: The page's steps:
     1. Format the card FAT32 / MBR.
     2. Load the official .DAT; the browser builds the recovery files.
     3. Copy them to the card.
     4. Unplug USB.
     5. Boot from SD using the per-model combo (shown dynamically).
     6. Run the normal on-screen firmware update to flash the official DAT.
   The project's README warning is "DO NOT FLASH CUSTOM FIRMWARE TO YOUR CAMERA WITHOUT
   DUAL BOOTING FIRST".
   Applies to: EXR II bodies listed on fujimod.com. Fully ready only for the X70; the
     X-T1 5.52 is listed as "Needs an owner" for testing.
   Evidence: CLAIMED for X-T1. The "sd-recovery" stage is not-run on hardware.
   Needs: SD card, official FWUP0005.DAT. Cost ~free.
   Sources:
     https://fujimod.com/recovery/
     https://fujimod.com/
     https://github.com/justjake/fujimod

3. TIREDBOFFIN'S PROPOSED UNIVERSAL ROUTE + ffre (EXR II NAND writer)
   What:
     - Patch the stage-0 loader from the standard DAT so that it loads seg4/seg5 from SD
       instead of NAND.
     - Optionally patch seg4 to open the update menu as if DISP were held.
     - The camera then boots entirely from SD and you re-flash with the normal updater.
     - Alternative: ffre, an unpublished loader that programs the NAND chip directly
       through the EXR II NAND controller.
     - One experiment called the loaded firmware's own NAND-program function to rewrite a
       single bad NAND block, and it succeeded (the model is not named).
   Evidence: ffre "partially tested only on XE2", "unpublished, abandoned / on hold".
     The single-block rewrite is VERIFIED per the author, model unstated. The universal
     route is CLAIMED: "all the pieces are available" but it was never fully implemented.
   Warning from the author: the cameras use raw NAND, so you must know the exact layout,
     ECC and bad-block handling. X-Pro1 NAND is "likely a bit different".
   Contact: fujihack Discord (https://discord.gg/UZXDktvAZP). Both maintainers send people
     there; "updates every day".
   Sources:
     https://github.com/tiredboffin/fffw (README: ffre)
     https://github.com/tiredboffin/fffw/discussions/10 (X-Pro1 brick; maintainer reply 2026-10-03)
     https://github.com/tiredboffin/fffw/issues/11 (maintainer: SD boot possible, WIP)

4. USB "JIG"/SERVICE MODE ff80 (VID:PID 04cb:ff80). Works only if the main firmware still runs.
   What: Power on while holding Shutter + Up with USB connected. Fuji's service jig
     protocol. The fffw ff80.py tool supports:
       bootrom dump (-s 0x4000), cfgdata read/write/load/save/dump, ram read/write/dump,
       rtc, syslog, diagdata
       xe2-specific (marked "do not use"): EEP load/save, jig on/off,
       "firmware -i <file>", "hack load/exec" (64 KB code)
   Limitation: the ff80 handler lives in the decompressed MAIN firmware (wiki "Route
     0xff80"). A camera whose NAND app firmware is broken will not enumerate. This
     matches the X-T1 in fffw #13, where no 04cb:ff80 device appeared.
     A cfgdata debug flag can make the camera boot straight into ff80 (this disables
     PTP). That is a "soft brick" you can undo through ff80.
   Evidence: VERIFIED as a working interface on the X-E2 (author) and the X-T50 (issue #11
     user backed up cfgdata through ff80). Not a recovery path for a dead-boot camera.
   Relevance to a "config save" brick: if the cfgdata/EEPROM write broke the boot but the
     firmware still reaches ff80, writing the backed-up cfgdata back with
     "ff80 cfgdata write/save" is the fix (SPECULATIVE but straightforward).
     PREVENTION: before any save, run "ff80 bootrom -o", "ff80 cfgdata dump -o" and full
     RAM dumps.
   Sources:
     https://github.com/tiredboffin/fffw (README)
     https://raw.githubusercontent.com/tiredboffin/fffw/main/ff80/ff80.py
     https://github.com/tiredboffin/fffw/wiki/Route-0xff80

5. MAIN BOARD SWAP (Fuji service or donor board / donor body)
   Fuji official:
     - X-T1 main-board replacement billed at US$293 (Fuji USA, F0/AF fault, ~2015-16;
       grips and port door also replaced). VERIFIED.
       https://www.fuji-x-forum.com/topic/3076-fuji-repairs-quote-for-xt-a-little-steep
     - Colombia service-centre quote of ~US$150 for an X-T1 main board. CLAIMED.
       https://www.fuji-x-forum.com/topic/6724-xt1-lens-control-error-message
       (cited via search summary)
     - X-T1 production ended in 2016. Fuji may now refuse the repair (parts-retention
       period). I found no current statement. A related report: Fuji called an X-E2S
       "uneconomic to repair".
   Third-party part:
     - Used X-T1 mainboard, eBay.de, seller in Shenzhen, US$228.
       https://www.ebay.de/itm/395342717095
     - X-T1 "for parts" bodies appear regularly on eBay.de, e.g.
       https://www.ebay.de/itm/317526310339
   Caveat (SPECULATIVE, but backed by service-manual structure): per-body calibration
     (cfgdata/EEPROM: sensor defects, PDAF, shading, serial/model ID) lives on the main
     board. Fuji's service manuals require "main board initialization" and adjustments with
     PC adjustment software after a board swap (the X-Pro1 manual says so). A donor board
     will boot, but image quality and AF may be slightly off. A whole donor body is often
     simpler.
   Home feasibility: moderate. The X-T1 is a weather-sealed body with many flex cables.
     There are iFixit board guides only for the X100T/X100F, not the X-T1.

6. OFF-BOARD NAND REPROGRAMMING (chip removal + programmer)
   Not found: no X-T1/X-E2 NAND part number, test points, UART or JTAG pads are published
     in any language. TechInsights/iFixit have no X-T1 board chip list.
   Known facts:
     - EXR II CPU0 is ARM Cortex-R4 (ARMv7 debug: 6 BP, 2 WP; debug ROM at 0xFFFD0000).
     - The boot-source selection bits are the low 3 bits at 0xFFF98000.
       https://github.com/tiredboffin/fffw/wiki/EXR-II-CPU
     - The SoC is FF4227 / FF4427 module (X100S was the first FF4427).
       https://github.com/tiredboffin/fffw/wiki/EXR-Processor-Family
     - The NAND is raw (not eMMC), so an off-board image needs the exact layout, ECC and
       bad-block map. Without a pre-brick dump of the SAME chip, cloning from a donor would
       also copy the donor's NAND-resident data.
   Evidence: SPECULATIVE. No one reports doing this on a Fujifilm X body.
   Needs: hot-air rework, TSOP/BGA NAND programmer (e.g. a TL866/T48/RT809H class tool,
     depending on package), a good image. Cost US$50-200 in tools plus high skill. This is
     the last resort; the SD boot path makes it largely unnecessary.

X-T1-SPECIFIC FAILURE REPORTS AND OUTCOMES
-------------------------------------------------------------------------------
- fffw issue #13 and fujimod issue #12 (same author "quanphoton", 2026-10-24):
    What happened: modified 5.52 packaged as "5.53" FWUP0005.DAT; the updater reported
      success; after a power cycle the camera was black with no LED.
    What failed to help: DISP/BACK at power-on; ff80 (Shutter+Up) not detected; SD
      diagnostic ffboot.bin/ffsys.bin (provisional, untested header); 4 key combos (listed
      in finding 1).
    Suspected cause: an early-loader hook at 0x41d5c redirecting to a stub at 0x6000.
    Outcome:
      - fujimod #12 was closed "not a bug in FujiMod"; the maintainer pointed to Discord.
      - fffw #13 was open with no replies at the time of research.
    UNRESOLVED.
    https://github.com/tiredboffin/fffw/issues/13
    https://github.com/justjake/fujimod/issues/12
- X-Pro1 (EXR Pro, sibling generation): same pattern. Modified 3.82 packaged as "3.83",
    dead with no LED. Unresolved; the maintainer described the SD stage-0 patch approach
    (finding 3). https://github.com/tiredboffin/fffw/discussions/10
- Official-firmware incidents: X-T1 4.20 AF-C freeze (pulled, 4.21 issued) and 5.50
    XC15-45 incompatibility (pulled, 5.51). Neither was a brick.
    https://www.photographyblog.com/news/fuji_finds_malfunction_in_latest_x_t1_firmware_update
    https://www.fujirumors.com/?p=76761
- Newer models after app-based updates: X-T30 / X-H2S units were fixed by Fuji under
    warranty; the method was not disclosed.
    https://www.fuji-x-forum.com/topic/33579-problem-after-firmware-update-through-camera-remote-app
    https://www.fuji-x-forum.com/topic/51624-x-h2s-dead-after-firmware-720-update-via-app
- Fuji's official line: "If firmware updating fails, the camera may no longer operate
    correctly". An incomplete update goes to an authorized service facility.
    https://fujifilm-dsc.com/en-int/manual/error_message_recovery/

-------------------------------------------------------------------------------
Q6: X-T1 SD-CARD BOOT (AE-L + Fn1). DOES IT WORK?
-------------------------------------------------------------------------------
- Source of the combo: the fujimod catalog (xt1/controls.json). It is derived from the
  key-to-GPIO mapping (GPIO 0-10 / 0-11), the same lines as the hardware-verified X70
  combo.
- Hardware status on the X-T1: NOT TESTED (progress "not-run").
- No public report of it working or failing on an X-T1. The only X-T1 brick report did
  not try exactly AE-L + front Fn1.
- Practical notes (from the fffw wiki):
    * hold the combo at power-on
    * FAT card
    * ffsys power-hold bit set (offset 0x10, bit 0)
    * smallest possible ffboot first (LED blink), which proves the ROM path without
      touching NAND
- Verdict: CLAIMED / promising, unverified on the X-T1.

-------------------------------------------------------------------------------
UART / JTAG / TEST POINTS
-------------------------------------------------------------------------------
Nothing published for any Fujifilm EXR II body, in any language searched. The Cortex-R4
has ARMv7 debug, so JTAG/SWD probably exists on the board, but the pads are
undocumented (SPECULATIVE). Canon has a documented UART (Magic Lantern); Fuji does not.

-------------------------------------------------------------------------------
PRACTICAL ADVICE FOR AN OWNER ABOUT TO DO A CONFIG/CFGDATA SAVE ON AN X-T1
-------------------------------------------------------------------------------
1. Before writing anything, while the camera works:
     - ff80 bootrom dump
     - ff80 cfgdata dump (the full EEPROM image)
     - RAM/firmware dumps
     - record checksums
   Make sure the backup can be restored without the camera's UI.
2. Prove the SD boot path FIRST, on the healthy camera:
     - build a green-LED card (fujimod.com, or ffboot LED code + ffsys with the power bit
       set)
     - hold AE-L + front Fn1 at power-on
     - confirm the LED pattern
   If this works, you have a NAND-independent escape hatch. If it does not, find the
   correct combo (or report to Discord) before risking a save. fujimod lists the X-T1 as
   "needs an owner" for exactly this test.
3. Only use cfgdata write/save in RAM first (it is not persistent until "cfgdata save").
4. If it bricks:
     a. try ff80 (Shutter+Up)
     b. try the DISP/BACK updater with the official FWUP0005.DAT
     c. SD boot recovery (fujimod recovery / patched stage-0)
     d. ask on the fujihack Discord (tiredboffin, justjake)
     e. Fuji service (if still accepted) or a donor board/body (~US$228 board; US$293 Fuji
        board swap historically)
